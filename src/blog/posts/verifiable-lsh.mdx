## Motivation

Nearest-neighbor search is easy to explain and annoying to verify.
The core problem is simple: once retrieval becomes approximate, proving that the returned candidate is the correct one gets much harder.

<Callout type="note" title="Why this matters">
  If the retrieval system is part of a larger proof pipeline, the verifier needs more than a final score. It needs evidence that the candidate selection itself followed the intended search procedure.
</Callout>

## High-level idea

The rough direction is:

- use LSH to cut the search space
- compute distances only inside candidate buckets
- enforce the final selection inside a proof-friendly circuit

That means the prover is not proving the full search over the entire dataset, only a constrained and auditable path through the retrieval pipeline.

## A tiny toy sketch

```ts showLineNumbers
type Bucket = { id: string; vectors: number[][] };

function chooseCandidate(query: number[], bucket: Bucket) {
  let bestIndex = -1;
  let bestScore = Number.POSITIVE_INFINITY;

  for (let i = 0; i < bucket.vectors.length; i += 1) {
    const score = l2Distance(query, bucket.vectors[i]);
    if (score < bestScore) {
      bestScore = score;
      bestIndex = i;
    }
  }

  return { bestIndex, bestScore };
}

function l2Distance(left: number[], right: number[]) {
  let sum = 0;

  for (let i = 0; i < left.length; i += 1) {
    const delta = left[i] - right[i];
    sum += delta * delta;
  }

  return sum;
}
```

The interesting part is not the loop itself. The interesting part is how to prove that:

1. the bucket was selected correctly
2. the distance was computed honestly
3. the minimum really is the minimum among the allowed candidates

## What usually goes wrong

- quantization decisions leak into the circuit design much earlier than expected
- hash-family choices that look harmless in the ANN prototype become expensive in proof land
- lookup-heavy layouts are easy to overengineer
